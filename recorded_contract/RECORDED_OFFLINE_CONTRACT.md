# Recorded-offline authority contract

Status: READY FOR CONTRACT REVIEW — proposed specification, NOT replay readiness.
Version: recorded_offline/1.0.0-draft.1. Base: a3c4f27f5f2f9307e7e4c645b54e55ee18668caa.
MUST/MUST NOT are normative. Schema covers shape; the semantic rules below are mandatory in addition to JSON Schema validation. No accepted code changes are part of this proposal.

## 1. Domain and identity
Every package MUST declare classification recorded_offline, the exact contract version, a versioned policy ID and policy SHA-256. A recorded-policy registry MUST be explicitly configured by the operator/reviewer; input claims cannot register authorities. Unknown versions/policies MUST be rejected. No implicit synthetic conversion, fallback or shared ledger namespace is permitted. Synthetic fixtures used to test the new parser remain labelled test data outside any claims of genuine historical capture.
IDs are opaque non-secret strings, scoped to dataset_id. observation_id identifies one immutable revision; logical_item_id identifies its correction chain; capture_id identifies a receipt. Every record has exact file_sha256, payload_sha256 and a locator into the immutable file. Hashes use raw bytes, not a reserialized payload. The complete package digest hashes exact package bytes and is stored externally, not inside itself. Same ID plus different bytes is ID_COLLISION, never last-write-wins. Source IDs identify market/feed provenance, never account numbers. No credentials or notification recipients belong in packages.

payload_locator MUST be bytes:<offset>:<length> with nonnegative decimal offset and positive decimal length; reject out-of-bounds ranges. payload_sha256 hashes that exact raw range. Parse it using the codec/schema pinned for the source in policy. IDs and timestamps do not replace the source payload.
The external versioned policy MUST define: domain/version; authority registry digest; decision_system_id; per-source codec/schema and allowed roles; all five role rules (required boolean, max_age_seconds, age_anchor, permitted source/authority IDs); max_clock_uncertainty_seconds; allowed notification roles/events/states and require_entry_permission; input size/depth/count limits; conflict behavior WAIT; missing availability behavior DEFERRED; and transport_enabled=false/trading_enabled=false. Missing rules invalidate policy. Exact policy bytes MUST match policy_sha256. No inherited synthetic policy or production defaults. Multiple sources for a role require explicit selection/conflict rules; absent such rules, disagreement is WAIT.

## 2. Five distinct clocks
Each historical time is an explicit KNOWN or UNKNOWN object. KNOWN includes a UTC Z timestamp, a nonnegative uncertainty bound, authority_id and receipt reference; UNKNOWN contains null time/authority/reference/uncertainty and a reason. Merely populating KNOWN does not make it verified: semantic validation resolves the authority and evidence. All timestamps require valid Gregorian RFC3339 UTC seconds, optional microseconds, no naive times/leap seconds/NaN. Preserve original source representation in provenance if conversion occurred. Offsets require documented contemporaneous offset evidence; never use today's broker offset.

| Field | Meaning and constraint |
|---|---|
| market_event_at_utc | Time of represented market fact, e.g. completed candle close; does not prove receipt. Predicted future event time is payload metadata, not this field. |
| captured_at_utc | Time the exact payload was durably recorded by the stated capture system. A retrospective export may be much later than the market event. |
| available_at_utc | Proven time the exact version was accessible to the named decision system. Must cite a verified availability barrier/receipt, not infer from candle close. |
| scenario_established_at_utc | Proven original establishment of this scenario version. For replay-derived scenarios with no original execution record it MUST be UNKNOWN. |
| replay_executed_at_utc | Actual execution/audit clock, recorded at replay execution; never substituted for historical time. Null in a pre-execution input package; populated in the eventual report. |

For a KNOWN time t and uncertainty u use [t-u,t+u]. Availability is usable only if its upper bound <= historical_cutoff_utc. Proof of event-before-capture and capture-before-availability requires nonoverlapping ordered bounds (equality allowed). Overlap is CLOCK_ORDER_UNPROVEN -> UNKNOWN/DEFERRED, not invented precision. A plainly reversed interval is CHRONOLOGY_INVALID -> REJECTED. Event-time UNKNOWN prevents historical market timeliness claims. The initial supported authority chain uses capture of the decision system's actual receipt, therefore availability cannot precede this capture. A later export of an earlier receipt is a separate artifact: its creation time MUST NOT replace the original receipt time. Do not set uncertainty to zero unless the authority policy explicitly supports that precision.

## 3. Provenance and receipts
The receipt registry resolves receipt_id to immutable artifact_ref/hash, subject_id, subject_payload_sha256, source_id, decision_system_id, receipt kind, authority_id, signed/anchored time and uncertainty. The receipt verifier MUST check exact byte binding, integrity, issuer trust, clock evidence, retention chain and audience. Trust assertions inside an input are not proof. A digest alone proves content identity, not who possessed it when. If the receipt cannot be verified, its claimed time is downgraded in the assessment to UNKNOWN while the original claim is retained unchanged.
Permitted receipt kinds: source_event, capture, availability, scenario_establishment, derivation_completion. The timestamp field's evidence_ref MUST resolve to the matching kind and subject. Authority may differ by kind; source publication does not prove local decision availability. Reference paths are opaque offline artifact IDs, resolved only within an approved immutable input root; no URL fetching, traversal, reparse points, live reads or automatic credential loading. Retain exact source bytes privately; public reports may expose hashes/reasons, not broker exports.

## 4. Derived features and scenario versions
Every derived feature/scenario MUST list ALL required immutable input observation IDs, plus separately optional IDs, engine/config hashes and a derivation-completion receipt (or null). Required role coverage is defined by the pinned policy, not by caller selection. Resolve the entire dependency DAG; reject cycles, orphan IDs, cross-dataset references and undeclared dependencies. Optional data actually used become required lineage for this version. No missing news/yields/volume value may be replaced by zero or a neutral fabricated observation.
The maximum input availability upper bound is only a LOWER BOUND on when a derived output could exist. It is NOT proof that computation happened then. A historical derivative requires a verified derivation-completion receipt binding output, dependency hashes and engine/config. Its proven availability must be >= every mandatory input's availability upper bound and >= completion upper bound. Missing required input/proof propagates UNKNOWN through the dependency closure. Recomputed features may be inspected as retrospective analysis, with historical eligibility DEFERRED; they are not an original decision record.
Each scenario version preserves exact technical payload bytes/hash: direction, score, Point A/B, FTA/TA, invalidation, HTF, primary/nested/alternative hypothesis IDs and permissions. No score-to-permission mapping. News cannot grant permission or independently reverse direction. Any normalized view retains a lossless source field mapping. scenario_established_at requires an original scenario record binding its technical payload and dependencies, and cannot precede their proven availability/completion. New replay output has no historical establishment by default.
Target progression within an existing hypothesis is permitted under accepted D2 lifecycle rules; changing Point B alone does not require a new hypothesis. Gold PWL 4073.545 -> D1 IDM 4019.92 with intermediates 4058.97/4044.76 preserves lineage. Unknown historical IDM establishment means UNKNOWN availability, not structural invalidity. Do not assert that an obstacle was absent without source evidence.

## 5. Cutoff, corrections and ordering
Pin dataset manifest hash, policy hash, historical cutoff and original source sequences in every result. A replay ingestion sequence is never a historical sequence. Source sequence is comparable only within a capture stream; cross-stream ties use observation_id for deterministic iteration, not causal ordering. Unknown capture order that matters to a decision gives ORDER_UNKNOWN/DEFERRED.
Process correction graph topologically independent of input array order. supersedes identifies exactly one predecessor in the same source/logical-item chain; changed source identity requires a new chain and explicit reconciliation, never automatic supersession. Cycles, missing predecessors, competing replacement branches, changed logical identity or conflicting same sequence are rejected/quarantined with no eligibility. A correction becomes effective only at its own proven availability upper bound. At cutoff T choose the latest effective version, never an obsolete ancestor; future corrections do not rewrite earlier reports. If a correction could have been available by T but its availability is UNKNOWN, report HEAD_UNKNOWN and DEFER historical eligibility rather than certify the ancestor. Stale/invalid replacement must not resurrect the old version. A correction proven wholly after T leaves the older as-of version valid at T.
Staleness uses each role's explicit policy age anchor and max_age_seconds. No universal TTL is invented by this contract. Unknown anchor -> UNKNOWN; future anchor -> rejection; age > limit -> STALE/DEFERRED. Conflicting required evidence -> WAIT/DEFERRED. Explicitly optional absent evidence is reported missing and does not alone block eligibility, but must never be used as neutral confirmation.

## 6. Outcomes and notification events
Envelope invalidity -> REJECTED, no journal mutation. Valid but incomplete evidence -> assessment UNKNOWN or WAIT with notification_eligibility DEFERRED and reason codes. Only complete proven historical lineage may yield an ELIGIBLE assessment under the pinned policy and unchanged technical permission requirements. ELIGIBLE never means trade permission or actual delivery. A retrospective what-if result is separately COUNTERFACTUAL and cannot be reported as historical eligibility.
Separate append-only records: HYPOTHESIS_FORMED, HYPOTHESIS_REVISED, ELIGIBILITY_EVALUATED, NOTIFICATION_GENERATED, DELIVERY_ATTEMPTED, DELIVERY_CONFIRMED. In this offline phase only replay assessment/preview records are created; delivery endpoints are unavailable. Actual historical notification generation/attempt/confirmation can be claimed only from independently verified original receipts, each binding its object and timestamp. Without those receipts they remain UNKNOWN/NOT_EVIDENCED, irrespective of a plausible replay. No transport or trading execution is authorized.

## 7. Persistence and reproducibility
Separate recorded-offline database and dataset ownership marker; no import of production mutable journals. Key operations by domain, contract version, dataset digest, policy digest, cutoff, event ID and request digest. Identical retry returns same logical record; mismatched request with same identity fails atomically. Rejected operations change neither journal nor projection. Transactionally persist receipt verification, selected versions and decisions; crash recovery finishes or rolls back incomplete work without inventing a historical timestamp. Restart uses pinned bytes/hashes and policy, not current files or current clock. Supersession history and prior reports remain append-only. A subsequent trust revocation adds an audit finding; it does not silently mutate an earlier report.
Semantic output must be identical across replay runs/input permutations once order is established, excluding replay execution time, run ID and performance metrics. A single-writer lock prevents concurrent writers to the same ledger; differing datasets cannot share state. File integrity checks alone are not isolation against hostile concurrent replacement: snapshot into an approved immutable staging root and validate hashes under exclusive ownership before execution.

## 8. Versioning and review gate
Proposed dispatcher recognizes synthetic and recorded_offline explicitly with separate validators and policies. Existing synthetic APIs, accepted schemas, fingerprints and errors retain behavior. Unknown domain/version fails closed. Major version changes alter semantics; minor additions require explicit schema acceptance, never silent field ignoring. Draft.1 is not executable approval. Implement recorded components only after independent contract review; then require new conformance tests plus full accepted regression.
Local capture audit is needed to ADMIT particular authorities/datasets, not to define conservative rules. No local CSV currently gains trusted authority from this document. Unknown availability remains a valid input state, not a reason to invent timestamps. Replay readiness stays BLOCKED pending implementation, data audit and tests.
